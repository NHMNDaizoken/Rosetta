# Application-scoped records and objects

This milestone adds a v2 resource contract to the existing Core process,
PostgreSQL/PostgREST and SeaweedFS integrations. No registry, capability grants,
delegation, composition, GUI or new service is included.

## Contract and migration decision (before implementation)

The v1 record and object namespace historically belongs to a tenant. Existing
resources have no authoritative application owner, so migration must not guess
ownership from JSON, filenames, headers or the first caller. V2 uses separate
record tables and a separate object-storage prefix. V1 never accesses v2 storage.

V1 data/object routes are deprecated for application-private data. They retain
their payloads and tenant semantics only for an explicit operator-configured
`LEGACY_RESOURCE_CLIENTS` allowlist (empty by default). Local Compose explicitly
allows the three existing service-account fixtures, not the browser fixture.
Other callers receive 403 `legacy_resources_disabled`. This intentional access
tightening prevents arbitrary browser/new-client fallback to tenant-wide storage.
It does not change identity, registration or workflow routes.

The legacy allowlist is a separate operator permission, not an application grant.
Do not allowlist production browser clients or treat legacy storage as private.
If a registered client is deliberately also allowlisted, suspend/revoke still
blocks all v2 access; remove its legacy allowance or disable its IdP client to
remove the separate legacy permission as well.

Before upgrading, inventory legacy clients and data, assign owners out of band,
and enroll/activate their backend clients. Temporarily allowlist only trusted
legacy backend clients needing a migration window. Copy approved legacy records
and bytes through the owning backend's v2 APIs, update application references to
new record IDs, verify isolation and checksums, then remove the legacy allowlist.
No automatic reassignment, copy, deletion or deprecation-removal date is supplied.
Keep legacy data until its owner explicitly authorizes its disposition.

Apply additive migration 004 before the new Core image. Existing migrations and
legacy data remain intact. Migration reapplication is supported. Reverting to an
old Core disables v2 routes while retaining v2 tables/bytes, but also restores the
old unrestricted v1 caller policy: restrict ingress/clients before rollback.

## Identity and authority

Every v2 request requires normal live OIDC introspection, verified tenant
membership and `core-reader`; mutations additionally require `core-writer`.
Core signs only verified issuer, subject, client_id, tenant and writer status in
a private 30-second assertion for a distinct nonlogin resource API role.

PostgreSQL resolves the application from the registered `(tenant, issuer,
oauth_client_id)` and exact operator-enrolled `resource_subject`. The application
must be active and its enrollment enabled. Existing enrollments default to no
resource subject and grant no v2 access. No app ID, tenant ID, client ID or owner
header/body field creates authority. The public identity response stays unchanged.

The operator must verify the enabled confidential client and its exact Keycloak
service-account user ID through authenticated administration, verify its tenant
and audience mappings, disable browser/password login for that client, and set
`app_private.enrollments.resource_subject` to that ID through reviewed SQL.
Never infer this subject from a username or provision it from an API request.
Replacing a resource subject is a credential/identity rotation requiring operator
review; neither the old nor new caller can request rebinding through v2.

Browsers authenticate to their Layer-2 backend. That backend authenticates the
human, enforces domain/resource authorization and uses its own private service
credential to call v2. Do not deliver that credential or broad Core writer tokens
to a browser. Forwarded user/app headers are not delegation and are ignored.
This milestone supplies no on-behalf-of token exchange or human impersonation.

## Records and objects

`/v2/data/{collection}[/{id}]` uses the v1 methods, response fields, limits and
replacement semantics, with a server-derived immutable owner application.
Reads include owned records and individually shared records; only the owner can
create, update or delete. SQL forced RLS enforces tenant and app/resource access,
including when the private PostgREST boundary is called directly with a valid
internal resource assertion. Legacy and application-administration roles cannot
access these records or administer resource authority.

`/v2/objects[/{uuid}]` uses the v1 binary methods and bounds. PostgreSQL stores
immutable ownership and an authorized current-version pointer; SeaweedFS paths
are generated by Core under a separate tenant/owner/ID/version prefix. Each PUT
uploads a fresh immutable version and then publishes it only after another live
database authorization check. Failed/ambiguous publication may leave unreachable
bytes; it never makes them public or transfers ownership. Concurrent owner PUTs
use last successful pointer publication, not optimistic locking.

UUIDs are scoped to the verified tenant. PUT at another tenant's UUID can create
an independent object in the caller's tenant, never read/replace the foreign bytes.
Object DELETE tombstones metadata before returning 204. A tombstoned UUID cannot
be reused, preventing old shares from authorizing replacement content. Bytes and
superseded/abandoned versions are retained for operator-controlled reclamation;
DELETE means logical API deletion, not secure physical erasure. No background
garbage collector or destructive migration is introduced.

## Explicit read sharing

Only an active owning backend with writer authority may approve sharing by POST
`/v2/resource-shares` with exactly:

```json
{"resourceType":"record","resourceId":"LOWERCASE-UUID","granteeAppId":"LOWERCASE-UUID","action":"read","expiresAt":"UTC-ISO-TIMESTAMP"}
```

The resource must exist and belong to the caller; the grantee must be a different
active application in the same tenant with an enabled resource enrollment.
Expiry must be in the future and at most 24 hours away. The response is 201 with
`shareId`, resourceType, resourceId, granteeAppId, action and expiresAt. Each share
is the owner's explicit authorization, not a separate tenant-administrator or
business approval. No wildcard, tenant-wide, update/delete, resharing, transfer,
cross-tenant or capability/delegation grant is supported. Reader permission is
still required to consume a share. Reading a shared object includes future owner
versions of that same live object until the share expires or is revoked.

DELETE `/v2/resource-shares/{shareId}` revokes an owning application's share;
repeat revocation returns 204. Foreign/hidden IDs return 404. Share creation and
revocation append audit events atomically; failure to append rolls back the grant.
No caller supplies the owner, tenant, grant ID or approval state.

## Suspension, revocation and consistency

Pending, suspended and revoked apps receive 403 `application_access_required`
at v2 entry. Resources whose owner is inactive become unreadable by grantees
(404); suspending a grantee blocks its own v2 entry. Reactivating an application
through the existing independent-approval flow restores otherwise valid unexpired
shares. Revocation remains terminal and retains resources and ownership; it does
not disable a Keycloak client or transfer data. Disabling enrollment or clearing
its resource subject also blocks access. The legacy allowlist is not a v2 bypass.

Authority is reread for each SQL operation and object pointer publication. A
request already authorized/in flight may finish across a concurrent state change;
revocation is not remote cancellation or secure erasure. Later requests fail.
Object reads are rechecked after fetching bytes before returning them. Database
or identity failure fails closed. There is no positive app/grant cache.

Workflow execution remains tenant-scoped under its existing contract; do not put
application-private payloads in shared workflow variables. Workflow app isolation
and delegated human auditing require separate scope, not implied completion here.

## Verification and recovery

Run the existing foundation, registration, worker and recovery suites plus
the resource cases in `npm run test:applications` sequentially against an isolated
local test stack. The suite covers real OIDC apps, SQL RLS/ACLs, read shares, spoofing, inactive
apps, direct Core/PostgREST checks and actual service restarts. Backups must include
the new role, private metadata/shares, app records, enrolled subject bindings and
the v2 object prefix. The isolated restore suite verifies restored app isolation.
